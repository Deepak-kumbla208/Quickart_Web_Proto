Decision memo

QuickKart Tech Stack Recommendation

Ten concrete technology choices for the production build, each with the alternatives actually considered. A recommendation to review and challenge — not a locked decision.

Companion to quickkart-backend-reference.html — architecture there, technologies here

What this memo assumes

A small team (roughly 2–5 engineers) shipping a first production version, Singapore-primary with India as a named second market. Every choice below is sized for that. If those assumptions are wrong, several answers change — see the closing note.

The architecture is already settled in the companion document: a modular monolith first with named extraction boundaries, REST + OpenAPI, PostgreSQL with row-level security, a Postgres transactional outbox rather than Kafka, and PostGIS for service zones. This memo does not revisit any of that. It only picks the products that implement it.

On "don't rewrite the app" — read this before decision 01

The constraint is that there is no separate native mobile app: one responsive website serves desktop and mobile, and that same website becomes the Play Store listing. Nothing below breaks that. There is no React Native, no Flutter, no second codebase, no native Android UI anywhere in this memo.

That is a different question from whether the web codebase changes. Decision 01 does recommend moving off the current single-file vanilla build — but into another single responsive web app that still is the Play Store app. The prototype has done its job: it is now the working specification for what to build, not throwaway work.

Client & packaging
01

Client / frontend framework

hard to reverse
RecommendedSvelteKitone codebase, three route groups

The current vanilla build does not survive contact with the Play Store, and the reason is concrete rather than stylistic. quickkart.js contains zero history-API calls — routing is a UI.route variable and render() rebuilds innerHTML. In a Trusted Web Activity, Android's Back gesture maps to browser history, so with no history entries the first Back press exits the app — from the cart, from mid-checkout, from anywhere. That is a lost order, and it is not a bug you can patch around without real routing.

The same root cause produces the rest: no deep links (so a push notification cannot open an order), no code splitting (all three portals ship to every customer), and full-innerHTML re-rendering that already needed a manual scrollTop workaround to stop losing the reader's place. Add multi-tenant theming and 15 permissioned admin screens and the ceiling is obvious.

SvelteKit is chosen over the React option for three reasons that matter here: it is the smallest conceptual step from hand-written DOM code (no virtual DOM, no hook rules, no server/client component split), it produces the smallest bundles — which is what a TWA's launch feel actually is on a mid-range Android — and its service-worker and adapter support is first-party rather than a plugin. Budget to hold it to: under ~150 KB of gzipped JS on the storefront route.

Sequence the port; do not go dark. Move the customer storefront first — it is what ships to Play — then rider, then admin. The existing build stays running as both the reference and the fallback until each portal lands.

Also considered
Next.js / React — the safest hiring answer and a much deeper component ecosystem for the admin dashboard. Rejected as the primary only on bundle weight and on PWA support being a third-party plugin. This is the runner-up, and the closing note says exactly when it wins instead.
Keep vanilla JS — rejected. It cannot produce history entries, deep links or per-portal bundles without effectively becoming a framework you now also maintain.
02

Play Store packaging

moderate
RecommendedPWA + Trusted Web Activitybuilt with Bubblewrap

A TWA is the literal expression of "the website is the app": Play ships a thin native shell that opens your verified origin full-screen in Chrome, with no browser UI. There is no second codebase, no bridge layer, and a web deploy updates the app instantly without a Play review. Capacitor would bundle a copy of the web assets into the APK, which reintroduces exactly the store-review release cycle this approach exists to avoid.

What has to be true — per the PWA installability checklist: HTTPS; a manifest.json with name, short_name, start_url, display: standalone, theme_color, and 192 px + 512 px icons marked purpose: "any maskable"; a registered service worker; and an offline.html fallback. Then a assetlinks.json at /.well-known/ binding your domain to the app's signing certificate.

The failure mode to guard. If Digital Asset Links verification fails, the TWA does not error — it silently falls back to showing a Chrome address bar, and the app simply looks broken. Note that Play App Signing re-signs your app, so the SHA-256 fingerprint you publish must be Play's, not your local upload key. This catches almost everyone once.

Whose app is it? This is white-label multi-tenant, and a TWA points at one start_url — so one shared listing would force customers to pick a retailer on launch. Give each tenant its own subdomain, its own manifest and asset-links, and its own Play listing, all generated from the same codebase and the same build pipeline. The store listing is per tenant; the code is not.

Service worker scope, deliberately narrow. Cache the app shell, CSS, JS, fonts and icons. Never cache stock, cart, orders or auth — a grocery app that serves a cached "in stock" is worse than one that is briefly offline. Static assets cache-first, navigation network-first with the offline fallback, live data network-only.

Also considered
Capacitor — the right answer the day you need a native capability the web platform lacks (background geolocation for the rider app is the realistic trigger). It also keeps the single web codebase, so this is a cheap switch later, not a rewrite.
Cordova — effectively legacy; Capacitor supersedes it. No reason to start here.
Backend & data
03

Backend language & framework

hard to reverse
RecommendedNestJS on Node.jsTypeScript

The architecture calls for a modular monolith whose internal boundaries are enforced rather than aspirational. NestJS modules are that pattern in the framework itself — each bounded context (identity, catalog, inventory, orders, payments, dispatch, notifications) is a module with an explicit public surface, so a cross-module reach shows up as an import you have to write on purpose. When a module is later extracted, the seam already exists.

It also gives one language across the whole stack with a TypeScript frontend: shared types generated from the OpenAPI document, one toolchain, one set of hiring criteria for a team this size. @nestjs/swagger emits the OpenAPI 3.1 contract the companion doc requires as the source of truth.

Also considered
FastAPI (Python) — excellent contract-first ergonomics and the better choice if the team is genuinely Python-strong. Rejected only because a second language is real overhead at this size.
Go — the best runtime efficiency and the right answer for the dispatch service if it is ever extracted under load. Rejected as the primary: slowest to write the CRUD-heavy admin surface that is most of the near-term work.
04

Database & hosting

hard to reverse
RecommendedPostgreSQL on AWS RDSap-southeast-1

PostgreSQL is not really in question — the schema is built on row-level security, tenant_id policies, composite foreign keys and PostGIS service zones, all of which are Postgres features the design already depends on. The decision is where it runs.

RDS wins on fit rather than flash: first-party PITR and read replicas, PostGIS available as an extension, a Singapore region for PDPA and data residency, and no BaaS layer to pay for. That last point rules out the obvious alternative — Supabase's value is its auth, auto-generated API and realtime, and this design deliberately uses none of them, so it would mean buying a platform to bypass it.

One hard requirement on whatever pooling you run. Tenant isolation sets app.tenant_id as a session variable, and that silently breaks under transaction-mode pooling, where connections are handed to different requests mid-session. It must be SET LOCAL inside an explicit transaction, with the whole request in that transaction. Get this wrong and RLS either fails closed everywhere or, far worse, leaks across tenants. Use RDS Proxy or PgBouncer and test it deliberately.

Also considered
Neon — serverless Postgres with per-branch databases, genuinely excellent for CI (a real database per pull request). Worth adopting for preview environments even if production stays on RDS.
Supabase — the fastest start and its RLS tooling is first-rate, but the pieces that justify it are the ones this architecture replaces.
05

Authentication

moderate
RecommendedOwn the identity tables, buy the OTPTwilio Verify + your own JWTs

One constraint decides this: customers are unique per tenant, not globally — (tenant_id, mobile). The same person can legitimately be a customer of two different retailers on the platform with the same phone number. Hosted identity providers assume a globally unique identity per project, so this either forces one provider tenant per retailer (unmanageable) or a mapping layer that recreates the model you were trying to avoid buying.

Two further pulls in the same direction: authorization is already modelled in Postgres — roles, per-screen permissions, per-user overrides and store scope — because RLS policies need it in the database; and RLS needs the tenant on the connection, which means the session must be derived server-side anyway.

This is not rolling your own crypto. Buy the parts that are commodities and dangerous to get wrong: Twilio Verify (or MSG91 for India) for OTP delivery, expiry, attempt limiting and SMS-pumping fraud; argon2id from a maintained library for admin passwords; a maintained JWT library; a standard TOTP library for admin MFA. What you own is the users table you were always going to own.

Also considered
Auth0 with Organizations — genuinely models multi-tenant identity and would work. Rejected on cost at consumer scale and on adding a network hop plus a second source of truth for authorization.
Supabase Auth / Firebase Auth — both assume globally unique phone identity per project, which is the exact constraint that fails here.
06

API layer & gateway

easy to reverse
RecommendedREST + OpenAPI, gateway in-appALB in front, no gateway product yet

REST with an OpenAPI 3.1 contract, /api/v1 URL versioning, cursor pagination and idempotency keys is already settled in the companion doc, and GraphQL was already rejected there — three first-party clients do not have the field-shaping problem it solves. Nothing here reopens that.

What is a genuine choice is where the gateway functions live now. Those functions — TLS, JWT verification, per-portal scopes (customer:*, admin:*, rider:*), rate limiting, request IDs — are all required. In front of a single monolith, a dedicated gateway product is a second system to operate for no isolation benefit: put TLS and routing on an Application Load Balancer and the rest in a NestJS middleware and guard layer. Extract it into Kong or API Gateway on the day the first service actually splits out, which is the same day it starts earning its keep.

The one BFF the companion doc allows — customer home-screen aggregation — comes free: a SvelteKit server route is that BFF, composing sections, rails and live stock into one cacheable response instead of the fan-out the prototype does client-side.

Also considered
Kong / AWS API Gateway from day one — correct at multi-service scale, premature at one. Deferred, not dismissed.
GraphQL BFF — revisit only if the customer app develops a real over-fetching problem; it layers over these services rather than replacing them.
Runtime services
07

Real-time & push notifications

easy to reverse
RecommendedSSE + WebSocket over Redis; Web Push (VAPID)

Split by direction. Order status is one-way, so Server-Sent Events over a Redis pub/sub channel is the simpler mechanism and reconnects natively. Rider GPS is bidirectional and frequent, so a WebSocket with the Redis adapter, keeping the nodes stateless so no sticky sessions are needed.

Android push from a TWA is standard Web Push with VAPID keys — handled by the service worker you already need for installability, delivered as real Android system notifications. Chrome routes it over Firebase infrastructure internally, but you do not take an FCM SDK dependency to use it. This refines rather than contradicts the companion doc's "FCM/APNs" line: the transport is the same, the integration is the web-standard one, which is the only one available inside a TWA.

Two practical notes: Android 13+ requires a runtime notification permission, so ask for it after a real order rather than on first launch, and Play requires a privacy policy for apps that request it. iOS Safari supports Web Push only for home-screen-installed PWAs, which does not affect the Play Store target but does shape any later iOS plan.

Also considered
FCM SDK directly — needed only under Capacitor or a native shell. Adds a Firebase dependency that buys nothing in a TWA.
Pusher / Ably — removes the socket-scaling work; costs per-connection money for something Redis pub/sub already does at this scale.
08

Payments

moderate
RecommendedStripe, with Connectverify local wallet coverage first

Two problems have to be solved at once, and Stripe is the only candidate that solves both with one integration. First, per-tenant settlement: this is a platform taking payments on behalf of retailer tenants, so money must land in each tenant's account, not a pooled one — that is precisely Stripe Connect. Second, the platform's own SaaS subscriptions, which the companion doc already routes to Stripe Billing. One vendor, one webhook model, one reconciliation story.

It also matches the security posture already committed to: hosted fields keep card data browser-to-Stripe so you stay in PCI-DSS SAQ-A, and Stripe's webhook signing and idempotency keys are exactly the "webhook is the source of truth" model the architecture assumes.

Verify before signing. Cards and PayNow in Singapore are well covered. Confirm current GrabPay availability and, specifically, whether each method is supported under your Connect charge type — payment-method coverage on platform accounts is narrower than on standalone ones and does change. If a wallet the prototype offers turns out to be unsupported, that is a reason to reconsider, not a detail.

Also considered
Adyen — stronger APAC local-method coverage and a real platform model; heavier commercial onboarding, better suited once volume justifies it.
HitPay — Singapore-local, PayNow/GrabPay-first and cheaper on SGD fees; thinner platform and API tooling for multi-tenant settlement.
Infrastructure
09

Hosting & CI/CD

moderate
RecommendedAWS ECS Fargate + GitHub Actionsno Kubernetes

Fargate runs containers without a cluster to operate — no control plane, no node pools, no upgrades — while keeping the app in the same VPC and region as RDS and ElastiCache, which matters for both latency and data residency. Kubernetes is explicitly rejected: at one monolith and a small team it is a full-time operational commitment bought before there is anything to orchestrate.

GitHub Actions for CI/CD, AWS CDK in TypeScript for infrastructure so it is the same language as everything else. Migrations run as a one-off task before the service updates, not on container boot, so a rolling deploy cannot run them twice.

An honest caveat: "no Kubernetes" is not "no setup". You still own a VPC, subnets, security groups, an ALB, task definitions and secrets. Budget a real week for it. If that is a week the team does not have, Fly.io or AWS App Runner will get you to production faster, at the cost of some control and, for Fly, splitting your database and app across providers. Start Fargate single-service and RDS single-AZ; go Multi-AZ at launch, not before — this stack costs money from day one and the starting size should reflect having no customers yet.

Also considered
Fly.io / Render / Railway — meaningfully simpler and the right call for a team of two. Weaker data-residency and enterprise-procurement story when selling to retailer tenants.
EKS or any managed Kubernetes — rejected outright at this stage. Revisit only when multiple services genuinely need independent scaling.
10

Supporting infrastructure

easy to reverse
RecommendedS3 + CloudFront · ElastiCache · Postgres FTS · Sentry + Grafana Cloud

Assets & CDN — S3 + CloudFront. Product imagery is the bulk of storefront bytes; serve it resized and in modern formats from the edge. Cloudflare R2 is worth a look purely on egress cost if image traffic grows.

Cache — ElastiCache for Redis, in the same VPC. It is doing four jobs already named in the architecture: catalog and home-screen caching, the rider ready-queue, live GPS, and rate-limit counters. Namespace every key by tenant — cross-tenant cache bleed is the easiest multi-tenant bug to write. Upstash is the lower-ops, lower-cost alternative at v1 volume.

Search — Postgres full-text + pg_trgm, per the companion doc, which carries you well past the prototype's 86 SKUs. Move to Typesense or OpenSearch when you need per-tenant synonyms and sub-50 ms autocomplete, not before.

Observability — Sentry for errors, Grafana Cloud for OpenTelemetry traces, metrics and logs. Sentry is what the team will actually open every day; Grafana Cloud is where the tenant-tagged traces the architecture calls for land, on a free tier that suits this stage. Datadog is better and materially more expensive.

What would change this

Hiring is the single biggest variable, and it only touches decision 01: if the team you can actually recruit is React-shaped, switch to Next.js and accept the heavier bundle — a framework nobody can maintain is worse than a slower one they can, and every other row in the table survives that swap untouched. Team size cuts both ways: at two engineers, drop Fargate for Fly.io and ElastiCache for Upstash, because a week of AWS plumbing is better spent on the product; past roughly eight, the reasoning inverts and a dedicated gateway, extracted services and managed Kubernetes start paying for themselves. Short runway means shipping the storefront on the TWA path first and leaving the admin portal on the existing build longer than feels comfortable — it is internal, and no customer sees it. The one thing that would force a re-plan rather than a substitution is payment coverage: if PayNow or GrabPay is not supported under Stripe Connect's charge model, decision 08 has to be settled before anything else is built on top of it.

Recommendation for review, not a locked decision. Architecture, schema and production requirements live in quickkart-backend-reference.html; this memo only selects technologies to implement what is decided there. Vendor claims — particularly payment-method and Connect coverage — should be confirmed directly before commitment.
