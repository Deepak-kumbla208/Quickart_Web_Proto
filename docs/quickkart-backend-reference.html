QuickKart Backend Reference

Screens, roles, a multi-tenant PostgreSQL schema and the production hardening the prototype skips — a starting point for the real backend build.

Source inspected: QuickKart web dev prototype — assets/js/quickkart.js (~6,240 lines), single Web HTML build, mobile-responsive
● current — built & working today ● proposed — business feature from the brief, not built ● production — engineering must-have for launch ● view-only

How to read this doc. The prototype today is a single-tenant, client-side app — one store group ("Prabhas Trading Pte Ltd", trading as QuickKart), state held in localStorage, no server. Everything tagged current below is inspected directly from the code. Everything tagged proposed — the platform Super Admin, tenants, feature entitlement, and most of the database — doesn't exist yet; it's drafted from the brief for this document and marked accordingly rather than presented as built.

Two different kinds of "not built". proposed means a business feature the brief asks for that the prototype doesn't have — tenants, feature entitlement, customer accounts. production, used throughout §04, means an engineering requirement for launch that a meeting-level prototype deliberately skips — real auth, payment capture, inventory locking, observability. The first is scope; the second is non-negotiable regardless of scope. Don't read them as the same backlog.

01

Screen & portal structure

One login screen with three portal tabs (Customer / Admin / Delivery Partner). There are no credential fields anywhere: Customer is a single "continue" click, Admin picks an existing user from a dropdown, Delivery Partner picks an active rider from a dropdown. Admin's visible screens depend on the signed-in user's role and permissions.

Customer portal

current

Browse → cart → checkout → track. One shared demo session per browser (no real sign-up/multi-account system) — the session is { role:"customer", name:"Customer" }, and "my orders" is simply every order whose customerName matches that name.

Store auto-assignment is real today current — a customer never picks a store. resolveBranchForAddress() takes the selected address's postal code, estimateCoordsFromPostal() maps its first two digits to a hardcoded sector-centroid lat/lng (POSTAL_SECTOR_COORDS, ~80 sectors, falling back to central Singapore), and findServiceableBranch() returns the nearest active branch whose radiusKm covers that straight-line haversineKm() distance. It legitimately returns null — "we don't deliver to your area yet" — rather than defaulting to a store.

Two knock-on effects that are easy to miss: the resolved branch drives what the shopper sees in stock (customerActiveBranchId → withBranchStock, so browsing reflects that branch's inventory overrides, not the network catalog), and it stamps order.branchId, which is what scopes the order to a Store Manager and to that branch's rider queue.

It is real but deliberately crude: a two-digit postal-sector centroid, straight-line distance, and a single circular radius per store. No geocoding, no road network, no service-area polygons, no capacity or stock awareness in the choice. See §04 — Serviceable area for what this has to become.

Rider / delivery partner portal

current

Login picks from the active partner list. Assignment is branch-scoped — a rider only ever sees orders from their home branch. Dispatch is a real FIFO round-robin (tryAutoAssign): when an order hits ready_for_rider, or when a rider goes Ready, the branch's oldest waiting orders are matched against its ready-queue, oldest-waiting rider first. Because there's no job runner, it's called inline from both of those transitions.

EarningsComputed from completed deliveries at a flat fee per delivery.
Shift managementmodals: endShiftConfirm, shiftSummaryShift starts implicitly on going "Ready"; "End shift" shows a summary receipt — deliveries done, earnings, time on shift.

Super Admin / platform control

proposed

Not present in the code — a repo-wide search for "tenant" returns zero matches across all versions. The prototype has exactly one implicit organization baked in as seed data. What follows is drafted from your brief, for a platform layer sitting above today's per-org Admin portal.

Super Admin (platform) manages the roster of tenants — retailer organizations onboarded onto QuickKart (e.g. "Prabhas Trading / QuickKart", "Grace Supermarket") — and, per tenant, which platform features are switched on:

Grace Supermarket
☑ Promotions          ☑ Multiple Stores
☑ Scheduled Delivery   ☐ Loyalty
☐ Subscription

A feature switched off for a tenant should be hidden from that tenant's Admin sidebar entirely — a gate above today's per-user PERMISSION_SCREENS RBAC, not a replacement for it.

02

Roles & portal access

Five roles across the three portals. Admin-side access is genuinely role/permission-based; rider and customer access are scope-based, not RBAC.

Super Admin

Admin portal

Full access to every Admin screen. Only role that can create/edit other Admin users and tune the Store Manager permission template.

Access: implicit full access — the role is locked and short-circuits the permission check entirely.

Store Manager

Admin portal

Default template: Dashboard/Reports view-only, Stores/Orders/Inventory editable, Partners view-only. Users, Customers, Catalog, Brands, Categories, Home Screen, Business Settings, Promotions and Coupons are none by default.

Scope: only their assigned store(s) (storeIds); permissions further tunable per user.

Delivery Partner / Rider

Rider portal

Views and updates deliveries, marks items delivered/unavailable, tracks earnings. No admin-screen access at all.

Scope: orders at their home branch only, and only while marked active.

Customer

Customer portal

Browses, orders, tracks. No admin access. Demo login — one shared session per browser, no real account system.

Scope: n/a — open portal.

Tenant Admin proposed

Admin portal

Today's "Super Admin" scoped to one tenant, once multi-tenant lands — same full access, bounded to their own org.

Scope: one tenant, every store within it.

Feature access proposed — tenant-level.

Does the tenant's plan include this capability at all — e.g. is "Loyalty" switched on for Grace Supermarket? Set by the platform Super Admin on Tenant Feature Management. If off, the screen is gone for every user in that tenant, whatever their role.

User permission current — per-user, within a tenant.

Given the feature exists for the tenant, can this Admin user see or edit it? Governed today by PERMISSION_SCREENS × the user's role template × an optional per-user override — each of the 15 screens independently set to none / view / edit (Dashboard, Customers and Reports only ever offer none / view — there is nothing to edit on them).

How Store Manager permissions get assigned: a Super Admin opens Admin ▸ Users, creates or edits a Store Manager, sets their store scope, and can override any of the 15 screen permissions away from the role-template default — all on one per-user form (permissionOverrides). No separate matrix screen; the override lives on the user record.

03

PostgreSQL schema

Re-derived field by field from the prototype's actual State shape, the SEED_* constants and every object built at runtime — then hardened into something that can be run as a real multi-tenant SaaS product rather than a single-org app. ● marks the primary key; the grey caption on each card names where in the prototype the table comes from.

Schema-wide conventions

UUID primary keys, not sequential integers

Every table's id is a UUID. Sequential ints leak volume and let a tenant walk another tenant's IDs by guessing; UUIDs are also safe to expose in tenant-facing URLs and APIs. Use UUIDv7 specifically — it's time-ordered, so it keeps B-tree locality on insert-heavy tables like orders instead of fragmenting pages the way random v4 does.

tenant_id on the row, never via a join

Every tenant-scoped table carries tenant_id directly — including child and junction tables that could technically reach it through a parent. An RLS policy that has to join upward to find the tenant is slower and much easier to get wrong. See Tenant isolation for how drift is prevented.

Audit columns everywhere

Every table gets created_at / updated_at (timestamptz, UTC). Tables an operator edits also get created_by / updated_by referencing the acting user. Marked + audit and + actor on each card below rather than repeated as four rows per table.

Soft delete on core entities

A nullable deleted_at on tenants, stores, users, customers, products and the other masters they reference. A SaaS platform can't hard-delete rows that historical orders and invoices still point at. Pair it with partial unique indexes (… WHERE deleted_at IS NULL) so a deleted SKU's code can be reused, and default every query and RLS predicate to excluding them.

Uniqueness is per tenant, not global

A product SKU, coupon code, store name or partner code must be unique within a tenant — two retailers will both have a "WELCOME15". Same for customer identity: (tenant_id, mobile) and (tenant_id, email), so one tenant's customer never collides with another's. Global uniqueness would leak the existence of other tenants' data through constraint violations.

Index discipline

Every index on a tenant-scoped table leads with tenant_id, so RLS-filtered queries stay index-only. Money is numeric(12,2), never float — the prototype's JS floats are fine for a demo and wrong for a ledger. Snapshot columns (tax_snapshot, price at purchase) are deliberately denormalized and must never be back-filled.

Deliberately not tables. State.readyQueue (the per-store FIFO rider queue) and State.recentlyViewed are ephemeral and belong in Redis, not Postgres — the queue changes on every dispatch and every rider tap, and browsing history is analytics, not a record. State.notices is a transient toast buffer with no persistence at all. State.session and State.cart are per-browser today; the cart becomes a real table above because it has to survive login, the session becomes a JWT.

Tenant isolation. Every table in the tenant-level group carries tenant_id on the row itself — including the child and junction tables that could reach it through a parent (addresses, order_items, order_status_history, user_stores, user_permission_overrides, role_permissions, combo_items, home_section_tiles, store_inventory, cart_items, product_tags). Enforce with Postgres row-level security keyed on a session GUC — USING (tenant_id = current_setting('app.tenant_id')::uuid) — set from the request's verified token, never from a client-supplied parameter.

Denormalized tenant_id can drift, so make drift impossible. Give each parent a redundant unique index on (tenant_id, id) and point children at it with a composite foreign key — FOREIGN KEY (tenant_id, order_id) REFERENCES orders (tenant_id, id). An order_item can then never carry a different tenant from its order, and no foreign key can cross tenants, structurally rather than by trigger or convention. The same pattern covers the cross-entity invariant that an order's store_id and customer_id must resolve to the order's own tenant.

RLS is not on until it's forced. Table owners and superusers bypass row-level security by default, so the application must connect as a non-owning role and every tenant table needs ALTER TABLE … FORCE ROW LEVEL SECURITY. Keep policies simple column comparisons against an indexed tenant_id — a policy that calls a function per row, or joins upward to find the tenant, is both slower and easier to get wrong.

Only the platform group sits outside that boundary: plans, features, plan_features, permission_screens, tenants, tenant_subscriptions, tenant_features, tenant_usage_daily, platform_users and platform_audit_log — reachable only by the platform Super Admin, on a separate connection role.

Today's prototype is exactly one implicit tenant hard-coded as seed data (DEFAULT_COMPANY_PROFILE, the SEED_* constants). Going multi-tenant means turning those into the first row of tenants plus its scoped children — not a structural rewrite of the app itself.

04

Production-time implementation

What the prototype deliberately skips because it's a meeting artefact, and what a real build has to put back. Everything here is tagged production — engineering requirements for launch, not business scope. Reference points are how quick-commerce platforms (Blinkit, Zepto, Swiggy Instamart, Instacart, DoorDash) actually build each one.

Read this as a sequence, not a shopping list. Five of these actually block a first paying tenant going live: authenticated checkout, real payment capture, inventory reservation, GST-compliant invoice numbering, and admin audit logging. Everything else is scale and hardening you can stage — and several items (event bus, search cluster, service split) are explicitly not day-one work. Where a simpler Postgres-only path exists, it's named.

Authenticated checkout

The single biggest gap between the prototype and a real storefront.

Real customer identity and an auth gate at checkout

production

Today: one shared demo session per browser — { role:"customer", name:"Customer" } with no password, no account and no server. Every order placed on a machine belongs to the same notional person, and "my orders" is a string match on customerName. Anyone can place an order for anyone.

How production apps actually do this

Quick-commerce apps in this market are mobile + OTP, not email + password — Blinkit, Zepto and Instamart all open the app to a browsable catalog and only ask who you are when you commit. The flow is: browse and build a cart as a guest → hit checkout → OTP wall → return to the exact same cart. Losing the cart across that step is the classic implementation bug and the reason the cart is a server-side table in §03: the anonymous cart is keyed by a device token, and on successful verification the server merges it into the customer's cart (union by product, take the higher qty) before rendering checkout.

Mechanics: 6-digit OTP, 5-minute TTL, max 3 verify attempts, rate-limited per mobile and per IP to stop SMS-pumping fraud. Issue a short-lived access JWT (~15 min) plus a rotating refresh token in an httpOnly cookie on web / secure storage in the app. The token carries tenant_id, subject and role — but not the admin store scope, which is resolved server-side per request from user_stores so a re-assignment takes effect immediately instead of at token expiry. Email + password with verification is a reasonable secondary factor for account recovery. The admin portal is a different problem: email + password with mandatory TOTP MFA, since those accounts can change prices and cancel orders. Riders use OTP like customers.

Serviceable area & store assignment

Real today, but the crudest possible version of a genuinely hard problem.

Geospatial service zones and multi-store ranking

production

Today: the first two digits of the postal code map to one of ~80 hardcoded sector centroids, straight-line haversineKm distance is compared against each store's single radiusKm, and the nearest match wins (see §01). A whole postal sector collapses to one point, a circle ignores rivers, expressways and the coastline, and the choice is blind to whether that store actually has the cart's items or the capacity to pick them.

How production apps actually do this

Zones, not radii. Every operator draws real coverage polygons — PostGIS geography(Polygon) per store with a GiST index, so serviceability is a ST_Contains against a geocoded delivery point. The alternative, and what Uber/DoorDash-lineage systems favour for dispatch, is H3 hexagons (resolution 8–9): coverage becomes a set of cell IDs, membership is a hash lookup rather than a geometry test, and the same cells key demand heatmaps and surge. PostGIS is the pragmatic start here — it's an extension on the database you already run, not another system.

Geocode once, on save. Addresses store a real geography(Point) from a geocoder (OneMap for Singapore, Google/Mapbox elsewhere) at the moment the customer saves them, not re-estimated on every lookup.

Rank candidates, don't pick the nearest. Multiple stores will cover a dense address. Score them on road-network ETA from a routing engine (not straight-line distance), live stock coverage of this cart, current picking backlog and rider availability, then pick the best. Splitting a cart across two stores is a deliberate product decision — most operators refuse it and instead drop the unavailable lines.

Define the fallback explicitly. Today an out-of-range address returns null, which is honest. Production wants a ladder: exact zone → nearest zone within a tolerance buffer → capture the address as unserved demand ("notify me when we reach you") → block checkout with a clear message. That unserved-demand log is how operators decide where the next dark store goes.

Service architecture & API design

Where today's single quickkart.js state object would actually split, and when.

Modular monolith first — microservices only when something forces it

production

Start as one deployable with hard internal module boundaries: a package (and its own Postgres schema) per bounded context, cross-module access only through a module's published interface, never a direct table read. That gives you the boundaries without the distributed-systems tax — no network partitions, no distributed transactions, one deploy, one trace. Instacart and DoorDash both ran monoliths well past the scale this platform will see for years, and split by extraction under specific pressure rather than up front.

Split a module out when one of these is actually true, not before: it needs a different scaling profile (inventory writes vs catalog reads), a different deploy cadence, a different compliance boundary (payments), or a different language/runtime. Use the strangler pattern — route the module's traffic through a façade first, then move it behind that façade. When you do split, each service takes its tables with it; a shared database across services is the anti-pattern that gives you the coupling of a monolith with the latency of a distributed system.

Candidate service boundaries, in likely extraction order

Identity & auth (first out — every other service depends on it and it has a clean contract) · Catalog & merchandising (read-heavy, cacheable, low write rate) · Inventory (write-hot, concurrency-critical, the one that will hurt first) · Orders (the transactional core — extract last, it touches everything) · Payments (extract early if PCI scope demands isolation) · Delivery & dispatch (real-time, geospatial, its own latency profile) · Notifications (extract early — it's cheap, and it isolates third-party provider latency from request paths).

API style: REST, contract-first, /v1

production

REST over HTTP with an OpenAPI 3.1 document as the source of truth, written before the handlers and used to generate typed clients for all three portals plus contract tests. URL versioning (/api/v1/…) — it's greppable in logs, trivially routable at the gateway, and unambiguous in a bug report. Within a version, additive changes only; breaking changes get a new version, with Deprecation and Sunset headers and a stated window (six months is a reasonable default) before the old one is withdrawn.

Cursor-based pagination on every collection (offset pagination skips and duplicates rows on a list that's being written to, which order lists always are). Idempotency keys — a client-supplied Idempotency-Key header on every unsafe mutation, deduplicated server-side — on checkout, payment and status transitions, so a retried request can't place two orders.

GraphQL is not the primary contract here. Three first-party clients don't have the field-shaping problem GraphQL solves, and it buys resolver N+1 risk, harder HTTP caching and a much more awkward story for rate limiting and per-portal scopes. If the customer app later needs aggregation badly enough, add a GraphQL BFF over the same services rather than replacing REST with it. gRPC is the right choice for internal service-to-service calls once anything is actually split out — schema-enforced and cheaper on the wire than JSON.

Gateway with portal scopes, and only one BFF

production

Put a single API gateway (Kong, Envoy, or your cloud's managed equivalent) in front: TLS termination, JWT verification once at the edge, per-portal OAuth scopes (customer:*, admin:*, rider:*), rate limiting, request-ID injection. Portal scopes matter more than they look — they're what stops a stolen customer token from being replayed against an admin endpoint even if that endpoint's own authorization has a bug.

Skip per-portal BFFs at the monolith stage. Three BFFs in front of one monolith is three more deploys for no isolation benefit; the monolith already shapes responses per portal. The one case that earns a BFF is the customer home screen — it assembles sections, tiles, combos, several product rails and live per-store stock, which is exactly the fan-out viewHome() does client-side today. Collapsing that into one server-composed, cacheable response is a real latency win on mobile. Add it there and nowhere else until a second case proves itself.

Sync for reads and checkout, async for the order lifecycle

production

Reads and the checkout write path stay synchronous — the customer needs a definitive yes or no about stock, payment and the order. Everything downstream of a committed order is asynchronous: notifications, dispatch, analytics rollups, invoice generation and loyalty accrual all consume events rather than being called inline, so a slow SMS provider can't add a second to checkout.

Don't start with Kafka. Use the transactional outbox pattern: the order write and its event row commit in the same Postgres transaction, and a poller publishes them — that removes the dual-write failure where the order saves but the event is lost. At this stage the "bus" can be a Postgres outbox table plus a worker, or SQS/SNS. Kafka earns its operational cost when you need replayable log retention, multiple independent consumer groups over the same stream, or ordering guarantees per partition key — say it out loud as a threshold rather than adopting it on day one.

Whatever carries the events: version every schema and evolve additively, make every consumer idempotent on event_id (at-least-once delivery is the norm, so redelivery must be a no-op), and give every topic a dead-letter queue with a documented replay procedure. Checkout itself is a saga — reserve inventory → authorize payment → create order → confirm reservation — with explicit compensating steps for each failure; orchestrated rather than choreographed, because a failed checkout needs one place that knows how to unwind it.

Resilience built in, not retrofitted

production

Every outbound call — payment gateway, SMS, geocoder, routing engine — gets a timeout, a circuit breaker and retries with exponential backoff and jitter (without jitter, retries synchronize into a thundering herd). Bulkhead the connection pools so a hung geocoder can't exhaust the threads serving checkout. Define the degraded behaviour explicitly for each dependency: search down → fall back to Postgres category browse; geocoder down → accept the address and resolve the store asynchronously; notifications down → queue, never block the order.

Observability as a first-class concern

production

OpenTelemetry from day one — traces with tenant_id, order_id and store_id as span attributes so you can answer "what happened to this order" in one query, structured JSON logs carrying the gateway's request ID, and RED metrics (rate, errors, duration) per endpoint. Define SLOs that mean something operationally: checkout success rate, checkout p99, order-status propagation latency, dispatch time-to-assign. Alert on those, not on CPU. Tenant-tagged metrics also give you the per-tenant health view you'll need to answer a support ticket without a database session.

Money & inventory

The two places where a prototype shortcut becomes a real financial loss.

Real payment gateway integration & PCI scope

production

Today: handlePay(method) records the chosen method and marks the order paid. Nothing is charged, authorized or refunded. The four methods (PayNow, GrabPay, Card, Cash on Delivery) are labels in business_settings.

How production apps actually do this

Never let card data touch your servers. Use the gateway's hosted fields or mobile SDK so the PAN goes browser-to-gateway and you receive a token — that keeps you in PCI-DSS SAQ-A, the lightest scope, instead of SAQ-D. In Singapore that's Stripe or Adyen plus PayNow via a bank/PSP rail; in India, Razorpay/PayU with UPI as the dominant method.

The webhook is the source of truth, not the client. Create the order server-side in a pending_payment state → create the gateway order → client completes payment → the gateway's webhook confirms it. Verify the webhook's HMAC signature, handle it idempotently (gateways redeliver), and never mark an order paid because the browser said so. Reconcile against the settlement file nightly and alert on any mismatch — that reconciliation job is what catches both gateway bugs and fraud.

COD is its own workflow and is still the majority of orders in parts of this market: the order is confirmed but unpaid, the rider collects, and cash is reconciled against the rider's shift at handover. That needs a cash-collection record per delivery and a shift-level float reconciliation — neither exists today.

Inventory reservation — the prototype can oversell without limit

production

Today: checkout never decrements stock. stockCount is set by hand in the admin Inventory screen and read for display only. Two customers can buy the same last unit; a hundred can.

How production apps actually do this

Dark-store operators run tight real-time counts because a mis-picked order costs a redelivery. The standard shape is a short-lived reservation: at checkout, atomically decrement available stock and write a stock_reservations row with a TTL of 10–15 minutes; confirm it when payment captures, and release it via a sweeper when it expires or the customer abandons. The decrement must be atomic in the database — UPDATE store_inventory SET available = available - :qty WHERE … AND available >= :qty and check the affected row count, or SELECT … FOR UPDATE inside the checkout transaction. Read-then-write in application code is the bug this is designed to prevent.

At high contention on a hot SKU, row locks on a single Postgres row become the bottleneck. The usual escape is to move that counter into Redis with a Lua compare-and-decrement (atomic, single-threaded) and reconcile back to Postgres asynchronously — but only when measurement says you need it, since it trades away Postgres's transactional guarantee.

Two related requirements that fall out of this: the substitution flow becomes an inventory operation (releasing the original line's reservation and taking one on the replacement), and picking should decrement against physical rather than logical stock, which is where a real store's cycle-count process comes in.

GST-compliant invoicing & tax audit trail

production

Today: invoiceNo is genId("INV-") — a random five-digit number, so invoices are neither sequential nor collision-free. The HSN code on each line is fabricated from the product id. What the prototype does get right is taxSnapshot: the rate, name and inclusive/exclusive mode are frozen onto the order, so changing GST settings later never rewrites a past invoice. Keep that exactly as it is.

How production apps actually do this

Sequential, gap-free numbering per tenant per financial year, allocated from a database sequence inside the order transaction — tax authorities in both jurisdictions treat gaps as a red flag. Invoices are immutable once issued; a correction is a credit note referencing the original, never an edit. Retain for the statutory period (five years for IRAS in Singapore).

Singapore: GST registration number and full company particulars on the tax invoice, which business_settings.company_profile already models. India: GSTIN, a real HSN/SAC per line from product master data, place of supply, and the CGST/SGST/IGST split — plus e-invoicing with an IRN from the IRP above the turnover threshold, which is an API integration, not a template change. Multi-tenant makes this harder, not easier: each tenant has its own registration, its own number series and potentially its own filing calendar.

Real-time tracking & communications

Live order tracking and rider GPS

production

Today: the status timeline is real and complete (new → confirmed → picking → packing → ready_for_rider → picked_up → delivered, with cancelled/returned as terminals) but it only moves when someone re-renders the page. There is no rider location at all.

How production apps actually do this

Status: a WebSocket (or SSE, which is simpler and sufficient for one-way status) fan-out from Redis pub/sub on a channel keyed tenant:order:{id}, so the WebSocket nodes stay stateless and need no sticky sessions. Push (FCM/APNs) is the fallback when the app is backgrounded — and the primary channel for the moments that matter: order confirmed, rider assigned, arriving, delivered.

Rider GPS: the rider app posts location every 5–10 seconds, adaptively (faster while approaching, slower while idle) and batched to save battery. Write it to Redis with a short TTL and broadcast to the order's channel — not to Postgres, which at 5-second intervals is roughly 17,000 rows per rider per day of write amplification for data nobody queries after the delivery. Persist only a decimated breadcrumb trail per completed delivery, for dispute resolution and proof of delivery. Show the customer an ETA from the routing engine rather than a raw distance.

Transactional notifications across the lifecycle

production

Today: pushNotice() appends to an in-memory array trimmed to the last five entries. Order confirmation reaches the customer only if they're looking at the screen. The one real outbound channel is the "Send order on WhatsApp" button, which opens a share link.

How production apps actually do this

A dedicated notification service consuming the order-lifecycle events above, with a per-tenant template registry (each retailer wants its own voice and sender ID), a provider abstraction per channel (SMS: Twilio/MSG91; email: SES/SendGrid; push: FCM/APNs; WhatsApp Business API, which is the default order channel in India and needs pre-approved templates), and per-customer channel preferences with quiet hours. Deduplicate on (event_id, channel, recipient) so a redelivered event never double-sends. Retry with backoff into a DLQ, and track delivery receipts — an undelivered "rider is outside" SMS is a failed delivery.

Scale & hardening

Catalog search beyond array.filter

production

Today: itemMatchesQuery tokenizes the query and substring-matches a concatenated haystack of name, brand, category and tags across 86 seeded products, in the browser, on every keystroke. Perfectly adequate at this size.

How production apps actually do this

It stops being adequate at a few thousand SKUs per tenant, or the first time someone types "brinjal" and expects eggplant. There's a genuine middle step before a search cluster: Postgres full-text search plus pg_trgm handles stemming and fuzzy matching well into the tens of thousands of SKUs on infrastructure you already run. Move to Elasticsearch/OpenSearch (or Typesense/Algolia if you'd rather buy it) when you need typo tolerance with per-tenant synonym dictionaries, relevance tuning, faceting across many attributes at once, or sub-50ms autocomplete at volume.

Two multi-tenant specifics: index per tenant, or a shared index with a mandatory tenant filter and routing key — never rely on a query-time filter alone to keep tenants apart. And availability has to influence ranking, because showing an out-of-stock item first is the fastest way to lose a basket; either denormalize per-store availability into the index and accept staleness, or rank in the index and post-filter against live stock in Redis.

Caching layer

production

Redis, with every key namespaced by tenant — cross-tenant cache bleed is the multi-tenant bug that is both easiest to write and worst to ship. Cache the catalog, category tree and composed home-screen payload (TTL plus event-driven invalidation when a product or section is published), sessions and the JWT denylist, the cart (write-through to Postgres), the rider ready-queue and live GPS, rate-limit counters, and hot stock counters. Put HTTP caching in front of the truly static parts — product images through a CDN, catalog responses with ETags.

Rate limiting, fraud & abuse, admin audit logging

production

Rate limiting at the gateway: sliding-window limits per IP, per token and per tenant, with much tighter limits on OTP send/verify (SMS costs real money and pumping is an active attack), login, coupon application and search.

Fraud and abuse: velocity checks on new-account-plus-COD, device fingerprint and address reuse across "different" accounts, and coupon-abuse detection — the prototype's WELCOME15 has no first-order check, so it's currently infinite. Watch the refund path specifically: the out-of-stock wallet credit pays back 1.1× the item price as a goodwill bonus, which is a straightforwardly farmable loop once accounts are free to create. Cap goodwill credits per customer per period and score refund frequency.

Admin audit logging is the item most often deferred and most regretted. Append-only audit_events (§03) for every write on Users, Roles, Business Settings, catalog price changes and order cancellations — actor, action, entity, before/after, IP, timestamp. The prototype already forces a reason on admin cancellation and stores it in statusHistory; that's the seed of the right instinct, generalized to every privileged action. In a multi-tenant platform this is also what lets you answer a tenant's "who changed our delivery fee" without giving anyone a database session.

Backups, DR and horizontal scalability

production

Backups: Postgres point-in-time recovery via WAL archiving plus daily base backups, a cross-region replica, and — the part people skip — a restore that has actually been tested. An untested backup is a hypothesis. Start from RPO ≤ 5 minutes and RTO ≤ 1 hour and adjust once you know what an hour of downtime costs a tenant.

Scale: keep the application tier stateless so it scales horizontally behind a load balancer (which the session-in-JWT and cart-in-Postgres decisions above already enable). Read replicas for catalog and reporting traffic, PgBouncer in front of Postgres because connection count is the first ceiling you'll hit, and range-partition orders and order_items by created_at (monthly) once volume justifies it — retention and archival get much cheaper when old partitions can simply be detached.

SaaS operations

Consequences of selling this as a product to retailer tenants rather than running it for one org.

Tenant billing, subscription lifecycle & usage metering

production

The tenants.status ladder in §03 — trial → active → past_due → suspended → cancelled — has to be a real state machine with real consequences, not a label. A failed charge moves a tenant to past_due and starts dunning (a retry schedule plus an email sequence), a grace period follows, and only then does suspension take effect. Suspension is a degradation, not a deletion: the storefront goes dark and the admin becomes read-only so the tenant can still export their data and pay to reactivate. That requirement is precisely why tenants, stores, users, customers and products are soft-deleted.

Don't build a billing engine. Stripe Billing or Chargebee handles proration, tax on your own invoices, dunning and card updates; you keep tenant_subscriptions as the local projection and reconcile it from their webhooks. Meter what the plan limits — orders per month, active stores, active users, SKU count, notification volume — with a nightly rollup into tenant_usage_daily, and enforce it as a soft warning at 80% and 100% before any hard cap. A tenant discovering a limit by having checkout fail during their Saturday peak is a churn event.

Tenant onboarding & data lifecycle

production

Onboarding a tenant is a seeded transaction, not a manual insert: create the tenant, its default roles from the system templates, its first Tenant Admin, a starter business_settings row and default home sections — essentially what the SEED_* constants do today, promoted into a provisioning routine. Give each tenant a self-serve data export (their catalog, customers and orders) — several jurisdictions require it, and a tenant who knows they can leave is more willing to commit. Deletion on cancellation is a scheduled, reversible-for-N-days pipeline with a documented retention policy, not a cascade.
